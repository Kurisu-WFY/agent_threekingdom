# MCP 工具接入方案

## 结论

交通、天气、景区票价这类实时或半实时信息不应该进入 RAG 知识库，也不应该由大模型生成。它们应作为外部工具接入 Agent。

推荐分层：

```text
历史文化资料 → RAG
景点静态资料 → 结构化数据库
天气/火车/地图/人流/票务 → MCP 工具或 API 工具
```

## 12306 MCP

仓库：https://github.com/Joooook/12306-mcp

公开 README 显示它是基于 Model Context Protocol 的 12306 车票查询服务，适合处理：

- 12306 余票查询
- 列车过滤
- 过站查询
- 中转查询

运行方式：

```bash
npx -y 12306-mcp
```

HTTP 模式：

```bash
npx -y 12306-mcp --port 8080
```

项目配置样例：

```text
config/mcp_servers.example.json
```

## Agent 什么时候调用 12306

应该调用：

- 用户问“从成都到南充怎么坐高铁”
- 用户问“明天去南充还有没有票”
- 用户做路线规划，并且出发地不是南充
- 用户明确要求查询火车、高铁、动车、车次、余票、票价

不应该调用：

- 用户只问陈寿、三国志、蜀汉历史
- 用户只问景区内部游览顺序
- 用户只问文化讲解
- 用户问景区门票。12306 不是景区票务工具

## 缺参追问

缺少以下参数时，Agent 应先追问：

- 出发城市或车站
- 到达城市或车站
- 出行日期
- 时间偏好，如上午、下午、晚上
- 是否只看高铁/动车

## 返回结果整理

Agent 不应把工具返回的大表格全部塞给用户，而应二次整理：

- 推荐 2-4 个最合适车次
- 标注出发/到达时间
- 标注历时
- 标注席别和余票状态
- 提醒“以 12306 实时结果为准”

## 天气和景区票价

- 天气：应接天气 MCP 或天气 API，并在回答中显示查询时间。
- 景区票价：优先官方接口；没有官方接口时，用后台人工维护数据表。不要用大模型猜，也不要把过期攻略里的价格当事实。
- 开放时间/演出时间：同样应走官方数据或运营后台。

## 候选 MCP/API

### 天气优先方案

筛选条件：GitHub star >= 100。

1. 百度地图 MCP：官方仓库，适合中国 LBS、天气、路况、POI、路线规划。
2. 高德地图 MCP：适合中国城市天气、地理编码、POI、路线规划，支持 stdio/SSE/streamable HTTP。
3. Mapbox MCP：官方仓库，全球地理编码、POI、路径规划、路线优化强；中国业务优先级低于百度/高德。

排除项：

- `weather-mcp/weather-mcp`：功能丰富，但当前 GitHub star 低于 100，不纳入推荐。

### 景区票价方案

当前没有找到可靠的 GitHub 开源“携程景区门票 MCP”。可选路径：

1. 官方景区/文旅局接口：最适合上线，可信度最高。
2. 后台人工维护数据表：适合 Demo 和早期上线，运营可控。
3. SerpApi MCP：star >= 100，可用于搜索“官方票价页面/官方公告”，但搜索结果不能直接作为票价事实。
4. 官方 Fetch MCP：来自 `modelcontextprotocol/servers`，可抓取官方页面，但必须做 URL 白名单。
5. 飞猪/阿里旅行门票 API：有开放平台接口，但偏商家/授权场景，接入成本和资质要求较高。
6. 携程浏览器自动化/爬取：不建议作为上线主路径，稳定性、合规和反爬风险都高。

结论：景区票价不要优先找“携程 MCP”。如果没有官方票务 API，早期 Demo 应使用运营后台维护的 `ticket_price` 数据表，并记录 `updated_at` 和 `source_url`。

票务服务的详细实现见 `docs/ticket_service_design.md`。

住宿位置查询归入外部工具，不进入 RAG。早期用百度/高德 MCP 查询酒店 POI，酒店价格用后台维护的城市预算档位；酒店实时可订价如果要上线，最终仍应接 OTA 或酒店供应商正式 API。

## 风险

- 12306 接口可能变动，开源 MCP 会失效。
- 余票和票价是实时信息，缓存时间不能太长。
- 查询可能受到网络、12306 风控、节假日高峰影响。
- 该工具用于查询，不等同于完成购票。

## Nuwax 平台判断

公开资料显示 Nuwax 支持 MCP、A2A、开放 API、插件生态、工作流、RAG 知识库、数据表和私有化部署。因此它和 Dify、Coze 属于同一大类 Agent 应用开发平台。

差异判断：

- 类似 Dify/Coze：都能做 Agent、工作流、工具调用、知识库。
- 更像 Dify 的地方：强调开源、私有化、API、知识库和企业交付。
- 更像 Coze 的地方：强调插件生态、模板、低代码搭建和多端发布。
- Nuwax 自己更强调：Agent OS、沙箱执行、MCP/A2A、AgentFlow、AgentGroup、VibeCoding。

由于具体 agent 页面可能需要登录态，最终以平台后台实际可见的“工具/MCP/插件/工作流”配置项为准。
