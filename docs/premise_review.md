# 前提审查

## 已成立的前提

- 产品可以围绕“陈寿、《三国志》、蜀汉记忆、南充三国文化资源”形成差异化主题。
- RAG 是必要组件，因为三国文化内容存在正史、演义、民间传说、地方阐释之间的混杂风险。
- Demo 第一阶段应优先做“问答、路线、分层讲解、正史/演义辨析”，不宜一开始追求 AR、数字人、多语言等高成本能力。

## 存在风险的前提

- “动态人流、票务、天气、演出时间”不能靠大模型猜测，必须接入实时 API、景区后台或人工维护表。
- “官方战略方向、开园时间、景点票价、开放时间”等信息会变化，后续上线前必须核实日期和来源。
- “南充三国文化之源”的表达适合品牌叙事，但在学术回答中应降级为“地方文旅定位/地方文化叙事”，避免当作无争议学术结论。

## 信息缺失

- 目标 Demo 形态：网页、小程序、App 原型，还是后台服务。
- 数据来源清单：是否有老师提供的论文、地方志、景区展陈文本、官方开放数据。
- 景点清单：万卷楼、熊猫三国城之外，哪些景点必须纳入。
- 技术约束：是否必须使用某个大模型、向量数据库、前端框架或学校服务器。
- 演示范围：评审看重产品设计、技术实现，还是文旅内容可信度。

## 独立建议

先把 Demo 做成“可解释的文化路线 Agent”，而不是“全能文旅平台”。因为票务、实时调度、地图导航的真实接入成本很高，短期内更适合做成可插拔接口和模拟数据。
